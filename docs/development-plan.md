# Windows 媒体下载器统一开发计划

状态：实施基线 v3，2026-11-03，统合客户端开发、上游同步、独立内核更新与发行。产品名暂用 Media Downloader，发布前确定正式名称。
本文为唯一的范围、里程碑和工期基准。依据：[ParseHub 代码审查](../review/ParseHub-Windows-review.md)；详细设计：[设计方案](./design.md)、[内核更新设计](./engine-updates.md)。历史审查中的旧工期不作为当前排期。

## 总体路线

产品由客户端与独立解析内核组成。客户端负责界面、任务和用户数据；内核负责 ParseHub、平台适配和执行工具。两者通过版本化协议通信，作者更新后能够独立发布内核。

执行顺序：M0 可行性 → M1 内核修复 → M2 任务服务 → M3 桌面界面 → M4 内核更新 → M5 发行验收。更新所需的进程隔离、协议和版本字段从 M0–M2 就开始实现，M4 完成分发闭环，避免最后重构。

首版交付同时包含可安装客户端、可独立替换的内核、上游同步流水线、签名更新源和回滚能力。只完成下载功能或只构建 EXE，都不算首版完成。

当前进度：代码审查、设计及 M0–M4 本机工程链路已完成，后续进入 M5 安装与发行准备，详见[开发进度](./progress.md)。M4 维护工作流已编写，实际发布仓库、生产签名环境、远端 CI 和更新源部署尚未完成；这些与 M0 延期项、真实辅助技术/多显示器和发行验收一起保留为发布前门槛。本文不代表远端定时任务已运行或客户端已发布。

执行调整：按用户“暂时不验证这个，继续”的要求，干净 Windows/虚拟机验收延期到发布前，本轮不再查询或配置 Hyper-V。现有冻结构建和真实抖音样本证明技术链路可行，允许继续 M1 及后续工程阶段；更多平台样本继续积累，尚未完成的验收不再阻塞本机开发，也不视作通过。正式平台支持清单和发布门槛仍需完整验证。

最新优先级（2026-11-04）：根据用户认为现有界面未达到成熟产品要求的反馈，在 M5 前插入完整界面重构。当前交付 `0.1.0.dev9` 24 平台接入测试版，M5 尚未推进。视觉与交互成果见[改版报告](./ui-redesign.md)，不以测试数量代替产品体验验收。

## 目标与默认范围

交付一款普通用户无需安装 Python、yt-dlp 或 FFmpeg 即可运行的 Windows 桌面应用：粘贴分享文案，预览作品，选择目录，加入下载队列，查看结果和失败原因。

以下为规划假设，不是已完成的验证：

- Windows 10/11 x64，标准用户运行；中文界面优先。
- 首轮真实样本重点验证 B 站、抖音、小红书；按 2026-11-04 用户要求，客户端接入固定上游版本全部 24 平台，逐平台线上验收单独记录，不以模块加载成功代替下载成功。
- 单条作品的视频、图集优先；同一输入中支持多个链接，但不抓取账号主页或完整播放列表。
- Python 3.12、PySide6、ParseHub 固定提交、SQLite；后台进程运行解析与下载。
- 一名熟悉 Python/Windows 的开发者；以下均为人日，按每周 5 个开发日估算。

首版包含：解析预览、队列、取消、手动重试、历史、目录管理、按平台代理、手动 Cookie、安全存储、错误诊断、安装包，以及内核检查更新、一键安装和回滚。

首版不包含：暂停/持久断点续传、扫码登录、浏览器 Cookie 自动读取、客户端主程序自动更新、无人值守安装内核更新、全平台能力对齐、主页抓取、字幕编辑、转码编辑、云同步。图集首版整组下载；LivePhoto 通过验证后再列为支持能力。

画质选择只在解析器能提供可靠格式信息时出现；其他平台显示“当前可用格式”，不承诺统一的 1080p/4K。

## 开发顺序与里程碑

| 里程碑 | 人日 | 前置条件 | 交付物与退出标准 |
|---|---:|---|---|
| M0：可行性验证 | 2–4 | 无 | 三个平台真实样本、最小冻结 EXE、工具启动和取消验证；确认首发能力表 |
| M1：内核兼容与修复 | 3–5 | M0 | 必要补丁、统一 DTO/错误/进度、离线回归通过 |
| M2：任务服务 | 4–6 | M1 | worker 池、SQLite、状态机、凭据、文件提交、崩溃恢复 |
| M3：桌面界面 | 4–6 | M2 协议稳定 | 主流程可操作、设置/历史/失败恢复完整 |
| M4：上游同步与内核分发 | 4–7 | M2 协议稳定，M3 更新入口 | 上游跟踪、候选构建、签名更新包、检查/安装/回滚验收 |
| M5：发行验证 | 3–5 | M3、M4 完成 | 固定依赖、安装包、干净机验收、完整更新演练、测试报告 |
| 首版合计 | 20–33 | | 约 4–7 个工作周，按范围和验证结果调整 |

稳定公开发布另留 5–10 人日处理兼容、安装、诊断和反馈；合计 25–43 人日。平台接口变化、账号不可用、证书采购或环境等待不包含在开发人日中。内核更新设计从 M0 开始，更新链路验收完成后才算首版交付。

按一人串行推进的相对排期：第 1 周完成 M0 并启动 M1；第 2–3 周完成内核及任务服务；第 3–5 周推进界面与内核更新；第 5–7 周完成更新闭环和发行验收。具体日期在 M0 实测后确定，不把等待账号、虚拟机或发布资源的时间算作开发完成。

## M0：先证明产品可交付

工作项：

1. 获取完整上游仓库和锁文件，固定到审查提交 `75a99d6fc46e15c4b994d5245ea4518404088c99`，建立独立开发环境。
2. 为每个候选平台准备 10–20 条分类样本：普通作品、短链、图集、需登录、删除/私密内容。用用户自有或明确允许测试的素材。
3. 分开记录解析、下载、登录态、代理、格式、耗时和失败类别，避免只验证“拿到了 URL”。
4. 验证 B 站 Cookie 修复方向及实际格式能力；确认其他平台必须依赖的签名和原生库。
5. 最小 EXE 包含 UI、worker、yt-dlp/FFmpeg，验证打包后不递归启动自身；若启用 YouTube，再检查其额外运行时需求。
6. 在干净 Windows 虚拟机完成一条普通视频、一组图片、取消下载和中文目录验证。
7. 验证 Job Object、curl-cffi、asyncio 子进程与打包环境共同工作，测量冷启动、内存和安装包大小；证明同一 UI 可启动两个不同版本的独立内核包。

原始完整验收标准：每个进入首发的平台至少完成 10 条预期可下载样本，解析和完整下载成功率均达到 90%；该数值只作为内部验收目标，不是总体平台成功率承诺。登录、删除等预期失败必须正确分类。冻结构建在无 Python 的干净机可用，无后台子进程残留。按上述执行调整，未完成的样本覆盖和干净机项转入发布前验收清单。

失败处理：平台不达标就从首发平台移出或增加专项修复；打包/进程管理不成立就先修正运行方式，不进入完整 UI 开发。更新本计划的工期与支持清单。

## M1：建立稳定的内核边界

| 编号 | 工作项 | 完成条件 |
|---|---|---|
| CORE-01 | Range 探测改为流式响应 | 忽略 Range 的大响应不被完整读取；正常 Range 和单连接回归通过 |
| CORE-02 | 独立工具启动器 | 开发与冻结环境都能调用固定工具，路径不依赖系统 PATH |
| CORE-03 | B 站视频 Cookie 链路 | API/备用路径均能接收凭据，使用假凭据做契约测试，真实账号做独立验证 |
| CORE-04 | 回调与取消修复 | callback_kwargs 全链路透传；取消不误删其他任务文件 |
| CORE-05 | Windows 路径处理 | 保留名、非法字符、中文、长标题、同名任务有确定行为 |
| CORE-06 | URL 与能力清单 | 精确 host 判断；首发解析器显式加载，一个可选依赖失败不会阻止整个应用启动 |
| CORE-07 | 应用 DTO 与错误码 | UI 不依赖 ParseResult 子类或私有 info_json |
| CORE-08 | 进度适配 | bytes/count/percent 明确区分，未知 total 为 null，速度不由百分比伪造 |

将补丁独立保存在本地受版本控制的 ParseHub 源包中，记录上游 SHA 和补丁清单。先使用源码路径依赖；发行构建生成确定的 wheel。上游升级单独开变更并跑回归。

## M2：实现可靠任务服务

按以下顺序交付：

1. 数据迁移和任务模型；状态、attempt、revision 与事件幂等处理。
2. QProcess worker 通信，版本化握手、心跳、异常退出和自动补充 worker；支持显式指定内核路径与兼容版本。
3. 两个 worker，每个同时处理一个任务；下载初始每文件 2 连接、每图集 2 文件并发。解析任务也消耗 worker 槽位。
4. 预览、确认下载、重新解析、失败重试和显式取消。
5. 任务专属工作目录、完成前提交授权、同名输出原子占位、启动时核对未完成提交。
6. Cookie 加密存储、代理快照、凭据有效性提示、日志脱敏。
7. 历史查询、任务去重、应用重启后显示中断任务；attempt 固定记录内核版本和上游 SHA，内核升级不迁移应用数据库。

退出标准：运行期间崩溃或强制结束 worker，不丢任务记录、不误标完成、不删除其他任务文件；重启后任务为中断并可重新下载。取消确认后进程树退出；旧 attempt 的延迟事件不能改变新 attempt。

## M3：界面与交互

- 新建下载：粘贴、提取链接、逐项预览、选择输出目录、加入队列。
- 下载队列：状态筛选、阶段/进度、取消、重试、查看原因。
- 历史记录：搜索、打开文件、打开目录、重新下载、移除记录。
- 设置：下载目录、并发、按平台代理、Cookie、客户端/内核/工具版本、日志导出；预留检查更新、安装、回滚及等待任务完成的交互，并在 M4 接入真实服务。
- 完成新手空状态、网络失败、凭据失效、磁盘写入失败、目录缺失、处理中关闭应用等交互。

退出标准：无控制台完成全部核心操作；主线程不执行网络、媒体分析和文件合并；连续添加与取消任务时窗口仍能操作。无暂停按钮或其他尚未实现能力。

## M4：快速同步作者更新

维护端和客户端各有一条流水线，详细协议见 [内核更新设计](./engine-updates.md)。

| 编号 | 工作项 | 完成条件 |
|---|---|---|
| UP-01 | 上游分支/Release 跟踪 | 计划每 6 小时检查，支持手动触发；按 SHA 去重生成候选更新 PR |
| UP-02 | 补丁同步与兼容检查 | 本地补丁独立管理；冲突/API/依赖变化阻断自动发布 |
| UP-03 | Windows 内核构建 | 产物包含完整 worker 运行环境、依赖及需要的工具，不依赖用户机器已有环境 |
| UP-04 | 版本清单与签名 | 明确 app/protocol/平台兼容范围，验证签名、哈希、大小和清单有效期 |
| UP-05 | 客户端更新管理 | 手动检查、可配置后台检查、更新说明、一键安装、空闲切换 |
| UP-06 | 健康检查与回滚 | 新内核握手/离线自检失败回到已验证旧版，断电/断网不损坏当前版 |
| UP-07 | 发布演练 | 同一 UI 从 E1 升到 E2 并回滚，队列和凭据保留，活动下载不被替换 |

维护目标：不涉及协议和依赖破坏性变化的上游修复，检测后争取在 1 个工作日内完成验证与发布；上游发生大改时单独评估，不承诺所有提交自动上线。真实站点测试不放进不受信任 PR 的 CI，也不向上游代码或公共 runner 暴露生产凭据。

发布流程是“发现更新 → 候选 PR → 应用补丁 → 离线/Windows/真实样本验证 → 维护者确认 → 签名发布”。客户端只接收本项目验证并签名的版本。

退出标准：上游变更可生成可审查的候选更新；同一客户端能够检查、安装 E2、空闲切换、失败恢复并回滚 E1。所有版本包可追溯到源码 SHA 和构建记录；在线检查失败不影响已安装版本。

## M5：打包与发布

1. PyInstaller onedir 作为首选验证路径，打包 UI 和独立 worker；yt-dlp、FFmpeg 等工具放在只读 tools 目录。
2. 安装程序采用每用户安装，默认无需管理员权限；便携版可作为额外交付，但应用数据仍按设计保存在用户数据目录。
3. 固定 Python、依赖、工具和 Windows 构建环境；产物包含版本信息、上游 SHA、补丁版本、工具版本、许可证 notices 和 SHA-256 清单。
4. CI 跑 Windows 离线测试与冻结构建 smoke test；Ubuntu 继续保留核心兼容检查。
5. 在干净 Windows 10/11 x64 环境手动验收；明确“已验证系统版本”，不推断所有历史构建均兼容。
6. 发布前准备签名流程；证书若未就绪，记录测试包未签名，不诱导用户关闭系统保护。
7. 主程序采用完整安装包更新，解析内核采用 M4 独立更新；不在用户电脑自行 pip install、git pull 或下载任意新工具。
8. 从已安装基线内核升级到第二个签名内核，再演练回滚；验证活动任务不被更新打断、错误清单被拒绝、崩溃后仍可启动。

退出标准：下载主流程和内核更新链路均在干净机通过；安装包、内核包、版本清单、签名、校验值、版本说明及测试报告齐全。

## 各阶段共同遵守的架构约束

| 约束 | 从何时建立 | 后续用途 |
|---|---|---|
| UI 与 worker 独立进程，内核目录不可变 | M0 | 无需重装界面即可切换内核 |
| ParseHub 仅经适配层访问，补丁独立记录 | M1 | 上游更新集中适配，冲突可定位 |
| IPC 版本、能力列表、精确版本握手 | M1–M2 | 不兼容内核在执行前被拒绝 |
| 每个 attempt 锁定内核版本与配置 | M2 | 任务不混用版本，问题可复现 |
| 数据库与凭据由客户端管理 | M2 | 内核回滚不回滚用户数据 |
| 签名包、独立目录、原子切换、保留旧版 | M4 | 更新失败可恢复，下载不中断 |
| 真实样本与干净机验收 | M0、M4、M5 | 证明上游修复确实可用且可分发 |

## 测试矩阵与质量门槛

| 层次 | 必测场景 | 通过标准 |
|---|---|---|
| 内核 | 忽略 Range、206 异常、网络中断、403/429、未知长度 | 结果完整或明确失败，无假完成、无整文件探测缓存 |
| 调度 | 重复命令、旧事件、并发取消、worker 崩溃 | 状态与 attempt 一致，无串任务和误删 |
| 文件 | 同名任务、CON、中文、权限不足、空间不足 | 输出隔离、明确错误、已有文件保留 |
| 凭据 | 不存在/失效/更新、临时文件、日志 | 不输出明文 Cookie、代理密码或签名 URL |
| UI | 队列、预览失效、关闭、重启、主题/缩放 | 100%/150%/200% 缩放可操作，错误有下一步动作 |
| 发行 | 无 Python/FFmpeg、离线启动、安装覆盖 | 工具可定位，离线可看历史，用户数据保留 |
| 平台 | 首发能力样本集 | 发布报告列出成功数/样本数、条件及预期失败 |
| 内核更新 | 断网、错误签名、错误架构、不兼容协议、启动失败、旧事件、断电 | 当前版本仍可用；更新不混用 DLL；能够恢复或回滚；任务使用固定内核版本 |

内部性能目标：主窗口干净机冷启动约 3 秒内可操作；worker 完成初始化后约 1 秒内响应命令；取消约 2 秒内反馈，最多 10 秒完成强制终止。M0 测量并在必要时修订；不是已验证指标。

## 风险和调整规则

| 风险 | 提前动作 | 触发调整 |
|---|---|---|
| 平台接口/签名变化 | 首轮真实样本、能力表、固定内核 | 缩小首发范围或增加专项人日 |
| 打包和原生依赖冲突 | M0 冻结构建、干净机 | 更换工具执行方式，再估算 |

| 断点续传需求进入首版 | 明确源 URL 过期、分片校验成本 | 独立设计与估算，调整范围 |

## 第一批可执行任务

1. BUILD-001：建立 Python 3.12 环境、完整上游基线和依赖锁。
2. QA-001：创建平台样本清单及结果表，不提交凭据。
3. CORE-001：修 Range 探测并增加针对性回归。
4. BUILD-002：实现工具启动器、最小 worker 与冻结 EXE。
5. WIN-001：Job Object 终止树与中文路径验证。
6. UP-000：验证 E1/E2 内核独立路径与握手，确定更新源、CI 和签名密钥托管方案。
7. QA-002：输出 M0 结论，确定首发平台、实际资源预算及后续排期。

完成 M0 后，才把候选能力表改为正式支持清单。当前已开始开发预览版，尚未完成首版交付。
