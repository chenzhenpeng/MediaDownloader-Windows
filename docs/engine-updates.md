状态：实施基线 v2，2026-11-04。签名安装、空闲切换、恢复与回滚已在本机冻结客户端实现并验收；维护端工作流已编写，生产仓库、密钥和更新源尚未部署。详见 [M4 报告](./m4-report.md)及[发布配置](./release-setup.md)。

## 目标与边界

作者修复平台解析后，尽量无需重新发布界面和安装程序，就能把验证后的修复分发到用户电脑。

拆分三个版本：

| 版本 | 内容 | 变化方式 |
|---|---|---|
| app_version | UI、任务服务、SQLite、DPAPI、UpdateManager | 完整客户端安装包 |
| engine_version | worker、ParseHub、兼容补丁、Python 依赖、yt-dlp/FFmpeg 等执行工具 | 本项目签名的独立内核包 |
| upstream_sha | 所采用的 ParseHub 精确提交 | 记录在内核清单、诊断和任务 attempt |

用户看到例如“客户端 0.1.0 / 内核 2026.11.03.1 / ParseHub 2.4.0 @ 75a99d6”。版本号是示意，不是现有发布。

客户端不直接拉作者 master，也不自行升级 PyPI 包。上游发布版本和 master 提交都可以成为候选，但必须经过本项目验证再发布。每个已发布内核不可变，相同版本不能替换为不同字节。

## 维护端：发现、合并、验证、发布

```mermaid
flowchart LR
    U[上游提交或 Release] --> D[定时检查与手动触发]
    D --> PR[候选同步 PR]
    PR --> P[应用本地补丁]
    P --> C[契约测试与 Windows 构建]
    C --> R[目标平台样本验证]
    R --> A[维护者确认]
    A --> S[签名内核包与版本清单]
    S --> F[本项目更新源]
```

上游跟踪工作流已写为每 6 小时及手动触发，同时查询默认分支和最新 Release；尚未部署到远端仓库。用 SHA 与候选分支去重，上游无变化不生成重复 PR。与默认分支分离、且当前基线尚未包含的 Release 可成为候选。

候选 PR 包含旧/新 SHA、上游提交摘要、改动平台、公共 API/依赖变化、本地补丁应用结果、测试与内核包尺寸变化。检测到更新不等于自动合并或发布。

本地补丁按目的拆小并记录：补丁 ID、对应上游 SHA、回归测试、是否已经被上游吸收。优先把 Windows 兼容补丁贡献给上游；在上游接受前仍保留可重放补丁。上游已修复的问题在通过等价测试后移除本地补丁，避免重复修改。

适配层为唯一接触上游对象的应用模块。契约测试覆盖平台枚举、parse/download、结果模型、Cookie、代理、取消与进度；若上游 API 改动，尽量只改适配层。无需要求作者保持我们的 IPC。

更新分类：

| 上游变化 | 处理 |
|---|---|
| 平台 URL/接口/签名等纯 Python 修复 | 重新构建并验证独立内核，UI 通常不变 |
| Python 依赖、原生 DLL、Python 版本变化 | 重建完整内核运行环境，增加干净机验证 |
| 新平台/新格式 | 内核可先提供能力信息；UI 能表达才启用，未验证能力保持关闭 |
| IPC/产品模型不兼容 | 新协议并更新客户端；旧客户端继续使用兼容内核 |
| 本地补丁冲突或测试失败 | 阻断发布，人工修复，不让客户端尝试解决冲突 |

目标是普通解析修复检测后约 1 个工作日内完成验证发布。只衡量可控制的维护环节，不保证所有上游变更当天可用。

## 发布物与兼容契约

内核包是完整、可独立启动的 worker 运行目录，包含 Python 运行时、精确依赖、工具、资源及 notices。首版以整包更新换取确定性；差分更新以后基于实测体积再设计。

worker 握手返回 engine_version、upstream_sha、protocol_version、capabilities、工具版本。客户端调度时按能力判断，而不依赖某个内核一定包含所有平台。

签名发布清单的示意内容：

```json
{
  "schema_version": 1,
  "channel": "stable",
  "sequence": 42,
  "published_at": "2026-11-03T12:00:00Z",
  "expires_at": "2026-12-03T12:00:00Z",
  "engine_version": "2026.11.03.1",
  "upstream_sha": "75a99d6fc46e15c4b994d5245ea4518404088c99",
  "patchset_version": "1",
  "app_min_version": "0.1.0",
  "app_max_version_exclusive": "0.2.0",
  "protocol_version": 2,
  "target": "windows-x86_64",
  "artifact_url": "https://updates.example.invalid/engine.zip",
  "size_bytes": 123456789,
  "sha256": "<64 lowercase hex characters>",
  "inventory_sha256": "<64 lowercase hex characters>",
  "unpacked_size_bytes": 456789012,
  "file_count": 1700,
  "notes": ["修复某平台解析"],
  "key_id": "release-key-1"
}
```

以上为协议示意，不是部署地址或真实文件哈希。清单不包含自身签名字段；发布时对不可变原始 UTF-8 清单字节生成独立 Ed25519 签名，先验签再解析，避免 JSON 重序列化差异。公钥内置客户端，私钥仅在受保护的发布环境使用，普通 CI/PR 无法读取。

首版采用 GitHub Releases 资产及 HTTPS 清单，配置与 Latest 约束见发布配置文档；实际仓库尚未确定和部署。客户端只接受允许的源域名和下载重定向，验签以签名绑定的包哈希和逐文件清单为最终信任依据。首版使用单一发布渠道；测试版使用显式 beta 渠道，stable 不接收 beta。

保存已接受的最大 sequence，拒绝过期清单、远端降级或相同版本不同哈希。时钟异常只影响更新检查，当前内核继续运行。旧客户端无法理解新清单或协议时提示更新客户端，不尝试执行。

正常密钥轮换通过已信任密钥签名的轮换记录或完整客户端升级；密钥泄露时走受信任的客户端更新撤销旧密钥。发布签名不能只用 HTTPS 或未签名 SHA-256 替代。

## 客户端：安装、切换、恢复

```text
安装目录/engine/                     # 随客户端发布的基线，可兜底
%LOCALAPPDATA%/MediaDownloader/
  engines/<engine_version>-<hash>/
    payload/                         # 不可变的已验证内核文件
    release.json / release.sig       # 签名发布记录
    healthy.json                     # 自检成功后生成；缺失时不能选为当前版
  updates/staging/<update_id>/        # 未完成下载/解包
  engine-state.json                   # current、last_good、pending、generation
  update-policy.json                  # 最大 sequence、清单哈希、版本/包哈希映射
```

UpdateManager 属于主程序，worker 协议不提供修改更新指针、信任公钥或应用数据库的接口。各内核目录包含完整依赖，不跨版本共享可变 DLL 或 Python site-packages。

安装流程：

1. 首版提供“检查更新”按钮；可设置每 24 小时后台检查，默认仅提示，由用户点“一键更新”。断网不影响解析之外的本地功能。
2. 展示内核版本、影响的平台、下载大小和兼容信息，按清单验证签名、有效期、序号、架构、app/IPC 范围。
3. 下载到 staging，设置大小/磁盘预算，验证完整包哈希。失败不改 current。
4. 安全解包，拒绝绝对路径、越界路径、符号链接/重解析点、重复/大小写冲突条目及超额解压；只写 staging 子目录。
5. 核对签名绑定的 `files.json` 和完整文件集合后，将候选安置到独立版本目录，再从固定位置运行隔离自检，检查模块、工具与本地下载。自检不传入用户 Cookie，不强制访问真实平台；通过后再次核对文件并写健康标记。缺少标记的目录不能用于启动恢复。这样避免冻结 Windows 进程自检后移动目录时的文件占用问题。
6. 健康候选等待全部活动 worker 空闲；更新下载和校验可以与正常任务并行，但不替换运行中的文件。
7. 暂停新任务派发，记录 pending，原子写指针；启动新 worker 并完成 ready 握手后记录 last_good/current，恢复派发。
8. 任一步启动失败或超时，恢复之前验证过的 current，重启旧 worker；原任务和凭据保持不变，显示更新失败及原因。

指针写入采用同目录临时文件、刷新和原子替换；只保留校验通过的版本引用。单实例/更新锁防止并行安装。启动发现 pending 未完成时回到 last_good，并验证其包清单；状态文件损坏时回退随包基线。故障恢复不能信任 staging 中的可执行文件。

更新发生时不改变已有 attempt 的 engine_version；切换前等待 active attempt 结束，队列中尚未执行的任务使用新内核。若用户不愿等待，可以取消任务后更新。预览不持有可执行计划，下载阶段重新解析。

本地保留当前版、上一稳定版和随包基线。设置页可显式“回滚到上一版本”；正常回滚只在已验证且未撤销的本地版本之间进行，不降低远端清单防重放序号。包清理只删除无 worker 引用的旧版本。

用户可锁定当前内核，暂停手动安装与回滚；启动故障时仍允许安全恢复。更新检查可每 24 小时仅提示，默认不启用。信任配置损坏时禁用更新并使用可验证版本或随包基线，不阻止主程序打开。

内核握手失败、离线自检失败或明确的连续启动崩溃可自动回滚；普通 403/429、Cookie 失效或某条内容无法解析不触发自动回滚，避免把平台波动误判为版本故障。首次成功握手也不能代表真实平台均正常，仍需发行前样本回归。

## 运维、测试与验收

设置和诊断同时显示客户端、内核、上游 SHA、补丁和工具版本；任务 attempt 记录使用的内核，便于复现和定位。

必测：

- E1 → E2 升级和 E2 → E1 本地回滚，不安装或重启 UI、不迁移数据库。
- 无更新、断网、下载中断、磁盘不足、错误哈希/签名、过期清单、重放清单。
- 错误架构、app/协议不兼容、解包越界、候选 worker 无法启动和 DLL 缺失。
- 下载中更新、取消与切换竞争、切换期间退出、指针替换前后断电模拟。
- 版本锁定、旧 worker 延迟事件、新版启动失败、旧版恢复、基线兜底。
- 保留用户任务/凭据、更新日志脱敏，以及应用卸载后的数据保留规则。

退出标准：上述故障不会破坏当前可用内核；活动下载不被更新杀死；客户端能准确报告当前版本；候选更新只能执行通过签名和兼容验证的内核。

这套设计优先解决“作者修复后可快速发布到用户”的路径。整包大小、下载耗时和真实站点维护成本在 M0/M4 实测；不提前承诺秒级更新或零维护同步。
