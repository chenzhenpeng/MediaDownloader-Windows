# 组件拆分方案与实施边界

Worker 独立、完整组合更新/回滚、独立工具和本地目录已实现；完整/精简安装包双分发仍为后续事项。当前安装包继续完整携带离线所需组件。实现和验收见 [当前架构](./components.md)。

## 目标和现状

应用、官方 ParseHub wheel 已有不同更新入口，但当前执行环境仍包含 worker、Python、依赖、FFmpeg/ffprobe 和初始 ParseHub。执行环境 0.2.1 约 178 MiB；小型下载修复仍需要下载整包。

本地 0.2.1 候选目录实测未压缩体积：应用 Python 代码 372,263 字节，FFmpeg/ffprobe 合计 210,644,992 字节，site-packages 合计 240,417,785 字节。site-packages 包含初始 ParseHub，不能把这些数字作为互不重叠的压缩包体积。拆分后体积需由构建实际测量。

## 发布边界

| 单元 | 内容 | 更新策略 |
| --- | --- | --- |
| 应用 | WinUI、任务服务、数据库、凭据、更新协调器 | 客户端安装包 |
| Worker | IPC 服务、官方 SDK 适配、预览转换、网络检查、HLS 下载、文件验证、提交协议 | 本项目签名小包，独立版本 |
| ParseHub | 官方原始 wheel、dist-info、原包回执 | 官方 PyPI，保留上游版本及原包摘要 |
| Python 环境 | Python 嵌入运行时、固定 Python 依赖、环境契约 | 完整签名包，依赖/ABI 变化时更新 |
| 媒体工具 | FFmpeg 和 ffprobe，许可文件及版本清单 | 成对签名包；也允许显式配置本地目录 |

Python 不再包含应用 worker 和初始 ParseHub 代码。初次安装的完整包可同时携带这些独立目录，但它们仍是各自不可变的组件，而不是各存一套重复内容。

yt-dlp 暂留 Python 依赖包。当前 SDK 使用 Python 模块及其依赖，不能把单独一个 yt-dlp.exe 当作等价替换。未来只有在上游调用边界和依赖组合明确后，才考虑独立 Python wheel 层。

## 需要修改的代码边界

- `scripts/build_official_runtime.py`：现在复制整个 `src/media_downloader`、工具及原包。改成分别构建 Python 环境、worker、初始官方解析包和工具包；从完整锁定环境中分离 ParseHub 包及其 dist-info，验证其余依赖的闭包，不能只删目录而遗失共享依赖。
- `official_worker.py`：现在从解释器所在目录寻找 engine.json、site-packages 和 tools。改成接收一份已验收组合的明确目录，校验实际导入来源，不再按解释器目录推断组件。
- `worker.py`、`engine_server.py`：作为 worker 包入口；不打包 UI、数据库管理、更新协调器。共享 wire 数据模型与文件命名/清单函数成为明确的 worker 内部依赖，禁止 import 客户端 Qt 模块。
- `engine.py`：当前 Engine 同时表达环境及解析版本。改成分别描述组件和执行组合，最后再生成进程启动参数。
- `official_install.py`：当前原包回执绑定一个 runtime-reference。改成在完整执行组合中引用解析包，更新 worker 时保持同一 ParseHub 和依赖引用。
- `component_catalog.py`、`update_contracts.py`：目前签名目录主要识别 engine/parsehub。增加 worker、python-runtime、media-tools 类型及契约检查，不能仅增加 UI 按钮。
- `update_store.py`、`update_manager.py`：从单一 current 指针升级为一个完整组合指针。现有 pending/confirm/rollback 思路保留，切换对象改成完整组合。

## 启动与兼容契约

一个执行组合引用准确的组件 ID 和清单摘要：worker、Python 环境、ParseHub、媒体工具。版本号用于展示及排序，摘要和已验证回执用于确认具体字节。

Worker 声明支持的客户端协议、worker ABI、Python 范围、所需依赖和媒体工具能力；Python 环境声明 Python ABI、平台、架构和完整依赖版本。ParseHub 继续检查 Requires-Python、Requires-Dist 和 extras。版本范围检查通过不代表行为兼容，仍必须运行候选握手和自检。

启动器很小，随 Python 环境提供。它只读显式选择的组合，不扫描系统 Python、不运行 pip、不依赖可变的用户 PYTHONPATH。以隔离模式启动，仅向模块搜索路径加入已校验的 worker 和解析包目录，并验证模块实际来源。工具使用明确绝对路径；上游需要 PATH 时，只在该子进程中前置已选工具目录。

不为了每次 worker 改动发布新 Python 环境；只有 bootstrap、Python、原生依赖或兼容契约发生变化时才更新环境包。

## 更新事务

1. 读取并验证组件来源；本项目组件验证签名，官方 ParseHub 验证 PyPI 元数据、摘要和归档，明确区分两种信任来源。
2. 根据当前组合构造候选组合，只替换需要变化的组件；依赖不足时明确列出需要一起下载的环境包。
3. 下载至全新目录，检查文件清单和摘要；在独立进程运行导入、自检及工具能力检查。
4. 等当前任务结束，用一个原子操作提交完整候选组合指针。现有任务在创建时固定自己的组合，不在下载中途换组件。
5. 启动握手成功后确认；失败恢复上一完整组合。重启时处理未确认候选。
6. 清理时保留当前、上一组合及运行中任务引用的所有组件，不能只按最新版本清理目录。

不能让 worker、解析包、环境和工具各自写 current：中断时会产生未经验证的混合版本。回滚指同一新架构内的已验证组合，不要求兼容旧客户端或迁移旧环境布局。

## 本地工具和自备环境

FFmpeg/ffprobe 支持“随应用提供”“在线管理的工具包”“本地目录”。本地模式要求两者存在、可执行、架构和必要功能合格，记录路径及摘要；文件变化后重新验证。本地工具不冒充本项目签名组件，不被在线更新覆盖，也不被垃圾清理删除。

Python 第一阶段只支持官方完整环境包。以后若开放自备环境，应选择带契约的完整环境目录，并在隔离探测中验证 Python、依赖及启动能力；不接受只填 python.exe 然后自动修改用户依赖的做法。

## 设置页面

顶层维持“应用更新”“ParseHub 解析组件”“执行环境”。执行环境展开后展示 Worker、Python 与依赖、媒体工具，各自显示版本、来源和状态；提供一个“检查环境更新”，按候选组合协调安装，不要求用户手工配对版本。高级设置提供本地工具目录。

例如快手 HLS 下载修复应显示：Worker 可更新；Python 与依赖无需更新；ParseHub 2.4.0 不变；媒体工具不变。下载提示显示实际需要更新的组件及大小。

## 实施顺序与验收

1. 定义组合描述和兼容契约，抽取 worker 包，落地显式目录启动；完成纯本地组合的任务、取消、重启和回滚验证。
2. 接入 worker 签名包及组合更新事务；验证只改 worker 时完全不下载 Python、ParseHub 和工具，失败不影响当前任务。
3. 独立 FFmpeg/ffprobe 工具包和本地目录；验证缺失、版本不符、路径含空格、工具执行失败及修改后重验。
4. 接入完整安装包与精简安装包：完整包离线提供全部组件；精简包首次运行明确提示所需下载及大小。两种安装方式共用组件布局及回退机制。
5. GitHub Actions 分别构建并签名 worker、Python 环境及媒体工具，通过组合验收后更新稳定目录。官方 ParseHub 仍直接消费 PyPI 原包，不恢复自定义解析包发布链。

验收至少包括：现有平台的直接文件下载、39 分段快手样本、图集、多文件提交、取消清理、摘要错误、协议不兼容、依赖缺失、安装中断、握手失败和重启回滚。实际包大小与更新流量由构建及下载测试记录，不先承诺未经测量的压缩大小。
